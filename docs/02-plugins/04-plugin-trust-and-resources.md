# 插件授权、沙箱与资源配额

> **文档状态**：架构规划与当前落地边界
> **整理依据**：用户历轮确认 + “未单独确认项按推荐方案生成”的授权
> **说明**：技术参数的具体默认数值需要在模块实施时验证；本文不构成现网变更指令。

## 威胁模型
插件可能卡死、耗尽 CPU/内存、泄露凭据、滥用网络或读取与采集无关的数据。签名解决制品来源真实性，不等于解决代码可信性。进程级隔离主要限制故障传播，还需显式最小权限和资源边界。

## 授权模型
Owner 批准插件包及其能力声明；Host 校验实际系统权限。建议权限按 `read:proc`、`read:sys_net`、`read:service_status`、`remote:openwrt_metrics`、`local:tailscale_metrics` 等受控语义分类。需要新增权限的升级一律重新审批，不能自动继承更宽权限。

## 凭据与执行隔离
Newifi SSH 私钥、Agent 注册凭据、Push 私钥均由相应可信模块持有；不得注入普通插件环境变量、命令行或日志。需通过受限中介接口将采集结果返回，禁止插件获得全局用户或设备管理 Token。

## 多级预算
| 层 | 预算项 | 保护行为 |
|---|---|---|
| Scheduler | 周期、并发、Deadline、队列 | 拒绝或跳过低优先级任务 |
| Runtime | RPC 大小、最大结果行数、日志速率 | 拒绝无界响应 |
| OS | CPU、RSS、Tasks、FD、文件/网络访问 | 限额、隔离、终止 |
| Supervisor | 启动/健康恢复连续失败上限和指数退避（显式配置） | 同一 Desired Revision 隔离，等待 Owner 发布新修订 |
| Server | 下载并发、带宽及 Artifact 配额 | 限速，不拖慢正常上报 |

## 失败安全原则
采集不足与插件停用必须被标记为数据缺失，不得制造“零负载”或“服务运行正常”的伪数据。失效插件的状态更新必须可审计。N1 的业务服务不得成为 Plugin Host 的子进程或生命周期附属对象。

## 实施前必须核实
systemd 版本、cgroup v2 delegation、实际用户权限、必要只读系统访问、沙箱对 Tailscale/sing-box API 的影响。未验证前不能把 Resource Guard 的设计目标当作已经存在的 OS 强隔离。

当前 Agent 对账每次运行时检查受管插件健康；升级后保留一个前序已应用包，运行版本健康失败会尝试回滚到该版本。启动、下载、校验或恢复连续失败使用必须显式配置的最大次数和退避上下限，到达次数后隔离该 Desired Revision，新的 Revision 才清除隔离。隔离、退避和回滚关联持久化在绑定设备身份、带校验和、单写者锁及条目/字节上限的私有原子状态文件中；重启后先等待 Server Desired，再复验暂存包，不凭本地状态直接启动进程。进程发现时延受控制轮询间隔影响。现有实现不限制 CPU/RSS、系统调用、文件或网络权限。上述 OS 资源与权限隔离仍需目标系统能力核验和专门故障验收。
