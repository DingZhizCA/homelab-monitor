# Home Lab Monitor 代码注释规范

本文统一 Home Lab Monitor 所有维护代码的注释风格，不限于 Go。适用范围包括：

- Go Agent 与 Server
- TypeScript / React Dashboard
- Shell 脚本与 Makefile
- YAML、JSON 等配置
- CSS 和其他后续引入的语言

项目当前处于开发和学习阶段，注释应兼顾语言学习、架构理解、后续维护和各语言
社区的常见风格。

总体原则：文件头说明职责和边界；协议及数据模型详细说明语义；公开 API 遵循
对应语言的文档注释习惯；函数内部重点解释“为什么”；显而易见的代码不写重复
注释。

## 1. 文件头说明职责与边界

新建的正式源文件原则上应包含文件级说明，重点回答：

1. 文件属于哪个模块或功能域；
2. 文件主要负责什么；
3. 文件明确不负责什么；
4. 文件位于哪条数据链路或调用链中。

不同文件应根据实际职责编写，不得机械复制同一个模板。文件头不要求逐项凑齐，
简单文件可以压缩为几行；复杂的协议、采集器和状态管理文件可以写得更完整。

Go 示例：

```go
/*
Package server implements server-side state for homelab-server.

本文件负责保存每台设备最新的 metrics snapshot，并保护并发访问。
本文件不负责指标采集、HTTP 编解码、历史持久化或 SSE 推送。

数据链路：HTTP metrics handler -> Store -> latest in-memory snapshots
*/
package server
```

TypeScript / React 示例：

```ts
/**
 * 设备详情 Dashboard 的页面编排层。
 * 负责把 REST/SSE 状态映射到卡片和趋势图，不负责指标采集或持久化。
 * 数据链路：Server API -> local history buffer -> ECharts/UI components
 */
```

以下文件可以不添加正式文件头：

- 工具自动生成且不应手工维护的文件；
- 内容极短、自解释的声明文件；
- 纯静态资源；
- 语言或框架惯例明确不推荐文件头的文件。

测试文件只有在测试边界或夹具语义不明显时才需要文件头，不为满足形式而添加。

## 2. 协议与数据模型是重点注释对象

以下内容应详细说明类型及字段的真实语义：

- Metrics 协议；
- HTTP Request / Response；
- Server 状态；
- Agent 配置；
- Collector 输出；
- Dashboard 使用的跨层数据类型。

字段注释优先解释：

- 业务含义；
- 单位；
- 数据来源；
- 时间代表采集、接收还是展示时间；
- `nil`、`null`、空字符串和零值的区别；
- 缓存值、缺失值和未采集值的区别；
- 选择指针、可选字段、联合类型或特殊数据结构的原因；
- 协议兼容性要求。

不要把“没有读取”和“读取结果为零”表达成同一种状态，也不要把缓存数据标成最新
采集数据。

## 3. 公开 API 遵循语言生态规范

### Go

导出的类型、函数、方法和常量遵循 GoDoc，注释以标识符名称开头。项目可以采用
“英文 GoDoc + 中文解释”的双语形式：

```go
// Store holds the latest metrics snapshot for each monitored device.
// Store 保存每台被监控设备最新的一份指标快照。
type Store struct {
```

### TypeScript / JavaScript

跨模块公开的复杂函数、Hook、组件属性和协议类型可使用 TSDoc/JSDoc。说明输入、
输出、副作用、时间单位和 `null` 语义；简单组件和自解释工具函数无需机械添加。

```ts
/**
 * 将最新采样追加到设备的浏览器内历史窗口。
 * 只维护临时展示数据，不代表 Server 已持久化历史记录。
 */
export function appendPoint(...) {
```

### 其他语言

遵循对应生态的文档注释格式和工具链约定。语言无专门规范时，采用简洁的文件说明
和邻近代码注释，不另造复杂格式。

## 4. 内部函数和局部类型保持克制

包或模块内部的小型 helper，如果名称、类型和实现已经清楚，可以不写注释。确实
需要说明时通常使用一到两行，重点解释约束或不直观的行为。

不要把每个内部函数写成小型技术文档。注释长度应与理解成本和错误风险相匹配。

## 5. 函数内部重点解释“为什么”

内部注释优先解释代码本身无法表达的信息：

- 为什么采用当前设计；
- 为什么需要锁、缓存、去重或特定超时；
- 为什么某个指标使用较慢采集周期；
- 为什么不能采用看似直接的系统调用；
- 浏览器可见性、网络重连或异步流程的约束；
- 当前实现对权限、功耗、安全或兼容性的影响。

推荐：

```go
// 使用独立 ServeMux，避免依赖可能被其他 package 修改的全局 DefaultServeMux。
mux := http.NewServeMux()
```

推荐：

```ts
// 温度使用传感器实际采集时间去重，避免 5 秒状态上报把一分钟缓存值
// 伪装成多次硬件测量。
```

不推荐：

```ts
// 设置 loading 为 false
setLoading(false)
```

## 6. 禁止无意义的逐行注释

以下注释不增加信息，应避免：

```go
i++ // i 加 1
return snapshots // 返回 snapshots
store.Update(snapshot) // 更新 store
```

```ts
// 遍历设备
devices.map(...)

// 发送请求
fetch(...)
```

注释不能只是把代码翻译成中文。重构命名或拆分函数能解决的问题，优先通过代码
结构解决。

## 7. 新知识点可增加教学注释

项目兼具学习用途。某个重要概念第一次出现时，可以比普通生产代码多解释一些：

- HTTP、REST、JSON、SSE；
- goroutine、channel、context、mutex / RWMutex；
- React state/effect、EventSource、浏览器可见性；
- ECharts 时间轴与 tooltip；
- `/proc`、`/sys`、Linux 系统指标；
- CPU delta 和 Network delta 算法；
- 文件系统、块设备、LVM/RAID 映射；
- 时间戳、单调时间和采样窗口。

教学注释应说明概念、项目为什么需要它、当前方案的取舍，以及必要时与熟悉语言的
差异。概念已经在项目中说明后，后续不要重复大段相同内容；可以引用现有设计文档。

## 8. 特殊设计约束必须保留

不容易从代码表面看出的项目级约束必须明确记录，尤其包括：

- HDD 最低功耗：后台监控不能仅为获取指标唤醒休眠机械盘；
- 主动刷新：只有用户明确授权后才允许执行可能唤醒 HDD 的操作；
- 数据时间：采样时间、Server 接收时间和缓存数据原始采集时间不能混淆；
- 协议兼容：新旧 Agent/Server 混用时的默认值与兼容处理；
- 并发安全：共享 map、订阅者和状态的锁或所有权；
- 权限与安全：凭据、token、文件权限和外部输入边界；
- 性能：限制历史窗口、采样频率或包体积的原因。

这类注释解释代码为什么“故意不做某件事”，不能因清理注释而删除。

## 9. 配置、脚本和样式的注释

### YAML / JSON 配置

解释非直观默认值、单位、唯一性和安全后果。例如 `device_id` 必须在所有 Agent
之间唯一，否则 Server 会将它们视为同一设备。不要在注释中放真实 token、地址或
其他秘密。

标准 JSON 不支持注释；相关说明应放在示例文件、schema 或文档中。

### Shell / Makefile

说明危险操作、环境前提、权限要求和不明显的命令选项。不要逐条复述普通命令。
示例命令应可复制执行，并避免使用范围不明确的删除命令。

### CSS

仅解释布局补偿、浏览器兼容、无障碍或难以看出的视觉约束。普通颜色、间距和字体
声明不需要逐行注释。

## 10. 注释必须与代码同步

修改行为时同时检查邻近注释、示例配置和设计文档。错误或过期注释比没有注释更
危险。

代码评审时至少检查：

- 注释描述的是当前行为，而不是原计划；
- 单位和时间语义准确；
- 没有泄露凭据或真实隐私数据；
- 没有把推测写成事实；
- 没有用注释掩盖难以理解的代码；
- 删除代码后没有留下孤立说明。

## 11. 详细程度分级

统一优先级如下：

| 对象 | 注释详细程度 |
|---|---|
| 文件头 | 较详细，说明职责和边界 |
| 协议、struct、interface、数据模型 | 详细 |
| 重要字段 | 详细说明语义、单位及缺失值 |
| 导出或跨模块 API | 生态标准文档注释 + 必要中文说明 |
| 内部函数 | 简洁，仅在需要时说明 |
| 函数内部关键设计 | 解释原因和约束 |
| 普通语句 | 通常不注释 |
| 显而易见的语法 | 不注释 |

## 12. 对 Codex 和其他代码生成工具的要求

生成或协助编写项目代码时，应自动遵守本规范，不等待用户重复要求：

- 新建正式源文件时主动添加合适的文件头；
- 新的数据模型字段主动说明语义、单位、来源和缺失值；
- 公开 API 遵循对应语言的文档注释风格；
- 新的 Go、Web、Linux 和网络概念重点解释设计原因；
- 已说明的概念不重复堆砌教学注释；
- 不生成逐行废话注释；
- 不为了注释覆盖率让注释数量超过实际信息量；
- 对自动生成代码遵循生成器规则，不直接加入会在下次生成时丢失的说明；
- 修改现有文件时改善本次改动附近的注释，不机械重写整个仓库。

最终目标不是“注释越多越好”，而是让未来阅读代码的人快速理解文件职责、数据
语义、关键设计决策和不明显的约束，同时保持代码本身简洁。
