# 存储、分层聚合与配额架构

> **文档状态**：运行时基础实施中；配额与分层聚合数据模式尚未实施
> **整理依据**：用户历轮确认 + “未单独确认项按推荐方案生成”的授权
> **说明**：技术参数的具体默认数值需要在模块实施时验证；本文不构成现网变更指令。

## 已确认存储方案
首版在 Alienware 本地 SSD 上使用 `mattn/go-sqlite3` 与 SQLite WAL。控制面元数据存入 `core.db`，高频指标存入 `metrics.db`；`core.db` 使用 `synchronous=FULL`，`metrics.db` 使用 `synchronous=NORMAL`。业务模块继续通过 Storage Repository 访问数据，不引入独立时序服务、Redis 或消息队列。SQLite 的单写入事务限制仍需通过真实 schema、批量写入和目标环境实测验证。

两个数据库文件必须位于同一个显式配置的私有目录中。运行时负责校验 WAL、同步模式、外键开关和每个连接的 `wal_autocheckpoint=0`，不静默退回其他模式。启用存储必须显式给出 checkpoint 检查周期、WAL 字节阈值和单次操作超时；任何一项缺失或非正值都拒绝启动。双库之间不提供原子事务；批次身份和对应指标必须同存于 `metrics.db`，需要审计的控制面变更及其审计事件必须同存于 `core.db`。

根模块故障测试使用独立子进程提交账户、插件 Desired State/审计和指标批次，在两个 WAL 仍打开且非空时直接终止进程，再通过正式 `storage.Open` 重开并执行 `PRAGMA quick_check`，验证控制状态、当前指标和批次幂等性可恢复。该测试证明当前开发机上的已提交事务可经进程崩溃恢复；它不模拟断电、SSD 缓存行为或目标主机文件系统。

当前第一版 `metrics.db` schema 保存批次 ID、设备 ID、内容 SHA-256、快照数，以及按设备和固定精度 UTC 采样时间索引的完整 `MetricEnvelope` JSON。原始历史适配器通过该索引流式读取范围内快照，复用 Dashboard Descriptor Registry 提取现有指标，并在达到请求点数时停止。全局采样时间和批次接收时间索引支持有界保留清理；指标拆列、聚合表和配额由后续迁移实现。

`core.db` 已有用户、服务端 Session、插件 Desired/Reported State 和通用审计事件 schema。认证仓储将首次 Owner、Owner 创建账户及角色/启用状态变更与对应审计事件放在同一事务，原子复核当前 Owner 和最后 Owner 约束；Session 只保存 SHA-256 Token 摘要。Session 过期清理周期仍未确定，当前后台任务只负责 WAL checkpoint，不删除业务数据。Dashboard、告警规则和 Incident 尚未接入该库。

## 数据域
| 数据域 | 主要数据 | 保护重点 |
|---|---|---|
| Core Metadata | 用户、Session、Device、Identity、Plugin、Desired State | 不受指标库清理影响 |
| Time Series | 原始测量、分钟/小时/日聚合 | 配额、自动过期、分层查询 |
| Flow Ledger | 设备方向、出站、Exit Node 账本及覆盖质量 | 长期一致性、去重 |
| Events / Alerts | 设备事件、Incident、规则版本与审计 | 不因插件卸载失效 |
| Diagnostics | 按需临时连接详情 | 单独配额、TTL、敏感权限 |

## 可配置保留架构
采样频率和上报频率属于 Collector/Agent；存储粒度、保留期限和硬配额属于存储策略。当前 C1 运行时要求显式配置原始快照窗口、较长的批次幂等凭据窗口、清理周期、每轮删除上限和单次超时。清理先按 `sampled_at` 删除过期快照，再按 `received_at` 删除超过凭据窗口且已经没有快照的批次身份；凭据窗口必须长于原始窗口。删除使用单事务和独立条数上限，数据库繁忙或超时时整轮回滚并等待下一周期，不改变 Agent 采样频率。

分钟、小时和日级聚合尚未实现。后续分层保留必须与当前数据库可用粒度、存储容量相互校验；在聚合落地前，原始窗口之外的数据不会被自动转存为长期汇总。

## 配额清理策略（已确认）
接近软配额预警，优先清理过期、低优先级原始采样；在满足用户策略的前提下尽量保留每日流量账本、关键告警及配置。接近硬配额必须限制新写入，禁止将 Alienware 系统 SSD 填满。元数据必须设置独立预留空间；重要数据也不具备无限保留特权。

## SQL 和后台任务
使用批处理插入、适量索引、有界查询、分页和点数上限。Server 按显式检查周期检查两个 WAL 文件；文件达到显式字节阈值且自上次成功操作后发生变化时，执行有单次超时的 `PRAGMA wal_checkpoint(PASSIVE)`。该模式不等待活跃 Reader/Writer，进程正常退出前也对两库各尝试一次；每次尝试记录数据库、原因、WAL 字节数、busy、日志帧、已 checkpoint 帧、耗时和错误。PASSIVE 只把可用帧同步回主库，不保证截断物理 WAL 文件；阈值基于文件大小，文件保持高水位后，有新写入时会在后续检查周期再次尝试。

删除数据不等同于立即回收 SQLite 文件空间。当前保留任务释放的页由 SQLite 后续复用；WAL 截断和数据库文件空间回收尚未实现。后续策略必须在低负载窗口验证，复杂的全库 VACUUM 不得影响正常 Agent 上报。

## HDD 约束
监控 DB 和写入工作目录放在系统 SSD，禁止周期性 SMART、磁盘遍历或其他会唤醒休眠 HDD 的任务。需要备份到 HDD 时必须由 Owner 单独审批唤醒策略。

## 演进触发
根据实际时序写入吞吐、查询 p95、保留容量和磁盘压力判断是否需要更换时序存储。必须通过 Repository/Export API 实现迁移，不让 Web Widget 直接依赖某个数据库 SQL 方言。
